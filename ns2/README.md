# ns2 — вторичный DNS на своей площадке (ESXi)

Второй нейм-сервер для `buten-ko.ru`: только DNS, без админки и без базы.
Забирает зону с ns1 по AXFR (TSIG), получает NOTIFY при каждом изменении,
отдаёт запросы, если ns1 недоступен.

```
Интернет ──53──▶ MikroTik (dst-nat) ──▶ dnsdist :53  ──▶ PowerDNS :5300 (secondary)
                                          │
                                          └─ MaxQPSIPRule / MaxQPSRule: режет флуд,
                                             чтобы не забить канал офиса
```

dnsdist стоит спереди не для красоты: без него NXDOMAIN-шторм на 53 забьёт
общий канал и положит заодно 1С и RDP.

## 0. Сеть и доступ

Решено: **SSH наружу не публикуется вообще**. Управление — только из локальной сети
`192.168.88.0/24`; на время настройки открывается временный доступ снаружи, после — закрывается.
Наружу смотрит единственный порт: **53/tcp и 53/udp** (иначе второй NS бесполезен).

**Публичный адрес площадки — `91.228.63.183` (канал PTK2).** Через него же открывается
временный SSH на время монтажа. Проверено снаружи: сервисы на PTK2 отвечают
(443 отдаёт сертификат `*.ejik.site`), то есть обратная маршрутизация через второй канал
на этом роутере работает — отдельные правила mangle для ответов не нужны.

Что из этого следует для настройки:

- `SSH_ALLOW` в `ns2.env` по умолчанию `192.168.88.0/24` — этого достаточно для работы;
  временный внешний адрес добавьте на время монтажа и уберите после;
- наружу ns2 сам ходит к ns1 за зоной (исходящий 53/tcp) — это разрешено по умолчанию;
- для AXFR на ns1 нужно разрешить **публичные** адреса офиса, а не LAN-адрес виртуалки:
  трафик выходит через NAT роутера. У площадки два PPPoE — `91.228.63.159` и
  `91.228.63.183`, поэтому в `--peer` передаётся список:
  `sudo ./enable-axfr.sh --peer 91.228.63.159,91.228.63.183`
  (TSIG всё равно ограничивает доступ ключом, список адресов — второй рубеж).

## 1. Что создать в ESXi

| Параметр | Значение |
|---|---|
| ОС | Ubuntu Server 24.04 LTS или 26.04 LTS (см. раздел «Про версию ОС») |
| vCPU | 1 |
| RAM | 1 ГБ (хватает 512 МБ, гигабайт — с запасом) |
| Диск | 10 ГБ |
| Сеть | статический IP в LAN, шлюз — MikroTik |
| Публичный IP | статический белый, тот же, что пойдёт в glue-запись |
| Имя | `ns2` |

После установки: `apt update && apt upgrade -y`, создать пользователя с sudo
или работать через root по ключу.

## 2. Порядок работ

### Шаг 1 — на ns1 (primary), включить отдачу зоны

```bash
sudo /opt/buten-ddns/scripts/enable-axfr.sh --peer <IP_NS2>
```

Скрипт: делает бэкап `pdns.conf`, добавляет `primary=yes`, `allow-axfr-ips`,
`also-notify`, генерирует TSIG-ключ и **печатает его secret** — он понадобится на ns2.
В конце перезапускает PowerDNS (~2–3 секунды без ответа; TTL записей 300 с,
поэтому для клиентов это незаметно).

Если нужно откатить: `pdns.conf.bak-<дата>` лежит рядом.

### Шаг 2 — на ns2

```bash
git clone https://github.com/Butenko-olek/DDNS.git /tmp/ddns-src 2>/dev/null || true
# скопировать каталог ns2 из проекта (scp с вашей машины или из этого архива)
cd /opt/ns2
cp ns2.env.example ns2.env
nano ns2.env          # ZONE, NS1_IP, TSIG_SECRET, SSH_ALLOW
sudo ./setup-ns2.sh
```

Скрипт поставит Docker, UFW, fail2ban, поднимет dnsdist + PowerDNS, импортирует
TSIG, создаст зону как вторичную и дождётся первой передачи. В конце — проверка.

### Шаг 3 — проверить, что ns2 отвечает

```bash
./check-ns2.sh
```

Скрипт сравнит число записей и serial с ns1 и дёрнет несколько имён напрямую по IP.

### Шаг 4 — проброс 53 на MikroTik

В `/ip firewall nat` (учётка `mcp` только читает, поэтому руками или через WinBox):

Как в существующих правилах этого роутера — по интерфейсу PTK2:

```
/ip firewall nat add chain=dstnat in-interface=PTK2 protocol=udp dst-port=53 \
    action=dst-nat to-addresses=<LAN_IP_NS2> to-ports=53 comment="ns2 DNS udp"
/ip firewall nat add chain=dstnat in-interface=PTK2 protocol=tcp dst-port=53 \
    action=dst-nat to-addresses=<LAN_IP_NS2> to-ports=53 comment="ns2 DNS tcp"
```

Правило `DROP DNS` в input-цепочке трогать не нужно: трафик на LAN-хост идёт
через forward, а не input (в forward стоит «drop WAN new, кроме dstnat» — наши
правила как раз dstnat).

Временный SSH на время настройки — тем же способом, и **не забыть удалить**:

```
/ip firewall nat add chain=dstnat in-interface=PTK2 protocol=tcp dst-port=22 \
    action=dst-nat to-addresses=<LAN_IP_NS2> to-ports=22 comment="ns2 SSH TEMP"
# после настройки:
/ip firewall nat remove [find comment="ns2 SSH TEMP"]
```

Проверка снаружи, с любой машины не из офиса:

```bash
dig @91.228.63.183 buten-ko.ru SOA
dig @91.228.63.183 prometall.buten-ko.ru A
```

### Шаг 5 — зона и делегация

1. В зоне поменять A-запись `ns2.buten-ko.ru` на новый публичный IP
   (через админку или `pdnsutil replace-rrset buten-ko.ru ns2.buten-ko.ru A <IP>`).
2. В панели reg.ru поменять **glue** для `ns2.buten-ko.ru` на тот же IP.
   `ns1` не трогать.
3. Подождать обновления зоны `.ru` и проверить:

```bash
dig +trace buten-ko.ru NS
dig @8.8.8.8 buten-ko.ru NS
dig @1.1.1.1 prometall.buten-ko.ru A
```

Приёмка: в `+trace` видно два NS с разными адресами, и оба отвечают.

### Откат

Одна правка: вернуть glue `ns2.buten-ko.ru` → `89.108.83.88` в панели reg.ru.
Сервер ns2 после этого можно гасить — он перестаёт быть нужен.

## 3. Что внутри

| Файл | Назначение |
|---|---|
| `docker-compose.yml` | dnsdist + PowerDNS secondary, без root, с drop capabilities |
| `dnsdist.conf` | лимиты QPS, TCP-лимиты, отключённая статистика наружу |
| `pdns.conf` | PowerDNS в режиме secondary, без API и веб-сервера (бэкенд LMDB — файл базы создаётся сам) |
| `ns2.env.example` | все параметры площадки в одном месте |
| `setup-ns2.sh` | установка и первичная настройка «под ключ» |
| `check-ns2.sh` | проверка: зона приехала, отвечает, совпадает с ns1 |

## 4. Про версию ОС

Стек целиком живёт в контейнерах, поэтому от версии ОС зависит немного: нужны только
Docker, UFW и systemd-resolved. Отсюда:

- **24.04 LTS** — та же, что на ns1: одинаковые команды, одинаковое поведение пакетов,
  меньше поводов для расхождений. Поддержка до 2029 (ESM до 2034).
- **26.04 LTS** — на два года длиннее срок поддержки (до 2031), новее ядро. Риск в том,
  что выпуск свежий и мелочи вроде имени пакета `docker-compose-v2` могут отличаться.

`setup-ns2.sh` написан так, чтобы работать на обоих: если в репозитории Ubuntu нет
`docker-compose-v2`, он сам переключится на официальный репозиторий Docker.
Единственное, что реально зависит от версии, — этот момент с пакетом, и он закрыт.

**Рекомендация:** если хочется единообразия с ns1 — 24.04; если важнее длинный срок
поддержки и не смущает свежий выпуск — 26.04, для двух контейнеров разницы не будет.

## 5. Что проверено на живом стенде (02.11.2026)

Комплект прогнан целиком на временном стенде рядом с рабочим сервером, без касания
продакшена. Найдено и исправлено три ошибки — именно поэтому стоит запускать
проверенный комплект, а не написанный «по памяти»:

1. **dnsdist не умеет имена хостов** в `newServer` — только IP. Поэтому в compose
   сеть задана статически (`172.29.0.0/16`, dnsdist .2, PowerDNS .3).
2. **`MaxQPSRule` в dnsdist 1.9.16 режет все запросы подряд**, включая первые:
   сервер молчит, в логах ни одной строки о запросе. Замена — `addAction(AllRule(),
   QPSAction(3000))`. Проверено перебором директив по одной.
3. **PowerDNS с sqlite не создаёт файл базы** — падает на старте. LMDB создаёт
   базу сам, схема не нужна.

Проверено в итоге: зона приезжает по AXFR (`AXFR-in zone: 'buten-ko.ru' ... zone
committed with serial ...`), запросы по UDP и TCP через dnsdist получают верный
ответ, `MaxQPSIPRule` не мешает нормальному трафику.

Ещё две грабли, не связанные с конфигами:

- **dnsdist подменяет адрес источника.** PowerDNS видит все запросы приходящими
  от dnsdist (`172.29.0.2`) и отвергает NOTIFY от ns1 с формулировкой
  `which is not a primary (Refused)`. Лечится PROXY protocol: `useProxyProtocol = true`
  на dnsdist и `proxy-protocol-from=172.29.0.0/16` на PowerDNS. Без этого зона
  обновляется только по таймеру SOA, то есть с задержкой в часы;
- **`pdns_control ping` в 4.9 не существует** — правильная команда `rping`;
- **новая зона не видна запущенному серверу** — после `create-secondary-zone` нужен
  `pdns_control rediscover`, иначе PowerDNS отвечает `REFUSED` на все запросы по зоне;
- **`set-meta` требует существующую зону** — сначала `create-secondary-zone`, потом ключ;
- **`pdnsutil replace-rrset` считает имя относительным:** `ns2.buten-ko.ru` превратится
  в `ns2.buten-ko.ru.buten-ko.ru`. Для поддомена указывать короткое имя (`ns2`),
  для апекса — `@`;
- **SOA refresh надо держать коротким** (в проекте 600 с): это страховка на случай
  потерянного NOTIFY — иначе вторичный не заметит изменения несколько часов;
- **systemd-resolved занимает 53-й порт.** На Ubuntu он слушает `127.0.0.53:53`,
  и Docker не сможет опубликовать 53 — упадёт с `address already in use`.
  `setup-ns2.sh` отключает stub-слушатель и переключает `resolv.conf` на не-stub
  версию (иначе сервер останется без DNS). Если ставите руками — сделайте это
  до первого `docker compose up`;
- если конфиг копируется на сервер через `scp` с Mac, файл приезжает с правами
  `600` — контейнер (uid 953) его не прочитает и молча упадёт. `setup-ns2.sh`
  ставит `644` сам, но при ручных правках помните об этом;
- в дампе зоны `pdnsutil list-zone` первая строка — `$ORIGIN .`. Если её удалить
  «для чистоты», все имена станут относительными и зона превратится в мусор.

## 6. Безопасность

- наружу открыт **только 53** (tcp+udp); SSH — с адресов из `SSH_ALLOW`;
  всё остальное UFW дропает;
- PowerDNS без `api` и без `webserver` — веб-поверхности нет вообще;
- AXFR только от ns1 и только по TSIG (`TSIG-ALLOW-AXFR` / `AXFR-MASTER-TSIG`);
- NOTIFY принимается только с IP ns1 (`allow-notify-from`);
- контейнеры: `no-new-privileges`, `cap_drop: ALL` + только `NET_BIND_SERVICE`,
  read-only корневая ФС, непривилегированный пользователь;
- fail2ban на sshd, unattended-upgrades для security-обновлений;
- dnsdist режет per-IP и общий QPS — защита канала от флуда и амплификации.

## 7. Ограничения, о которых надо помнить

- **Статический IP обязателен.** Glue-запись у регистратора не умеет меняться сама:
  сменился адрес — домен отвалился, пока не поправите руками.
- **AXFR и роутеры.** Пока ns1 лежит, обновления IP от роутеров не проходят;
  уже выданные адреса живут ещё TTL (300 с), а роутеры повторяют попытку каждую минуту.
- **Канал общий с офисом.** Даже с dnsdist мощный флуд забьёт uplink целиком —
  это цена размещения у себя. Если такое случится, спасение — приостановить
  проброс 53 на роутере, зона продолжит работать с ns1.
- **Питание.** DNS живёт там же, где всё остальное. UPS на роутер и ESXi — часть схемы.
