# Self-hosted DDNS

Свой собственный Dynamic DNS сервер: свой домен, свой PowerDNS, своя админ-панель — без сторонних DDNS-провайдеров, без ежемесячного подтверждения, без чужих лимитов.

Поддомен привязывается к текущему публичному IP устройства (роутера, домашнего сервера, ноутбука) и обновляется автоматически.

**Стек:** FastAPI (админ-панель + API обновления) · PowerDNS (авторитативный нейм-сервер) · PostgreSQL (хранилище для обоих) — всё в Docker Compose.


## Как это устроено

```
                    ┌──────────────┐
  роутер       ───▶ │   ddns-api   │ ───▶ PowerDNS API ───▶ postgres
  / скрипт          │  (FastAPI)   │                         (зона)
                    └──────────────┘
                           ▲
                           │ HTTP Basic Auth (браузер)
                    ┌──────────────┐
                    │ админ-панель │
                    └──────────────┘
```

- **`ddns-api`** — два вида эндпоинтов:
  - `/update` и `/nic/update` — сюда роутер/скрипт сообщает свой текущий IP. `/nic/update` говорит на том же протоколе, что No-IP/DynDNS (`hostname` + `username`/`password`, либо HTTP Basic Auth) — поэтому встроенные DDNS-клиенты большинства роутеров работают с ним напрямую.
  - `/admin` — веб-панель: добавить/изменить/отключить/удалить хост, посмотреть последний IP и свежесть обновления, скопировать готовую настройку под конкретный роутер, сменить пароль.
- **PowerDNS** — реальный авторитативный нейм-сервер для твоей зоны; `ddns-api` обращается к нему через HTTP API, чтобы менять записи.
- Зона PowerDNS и данные DDNS (хосты, токены, логин админки) живут в одном и том же Postgres.


## Что нужно перед началом

- Домен (или поддомен) под вашим управлением и с возможностью прописать NS-записи — например, `ddns.example.com`.
- Сервер с **публичным статическим IP** и открытыми портами **53/tcp**/**53/udp** (DNS) — можно совсем пустой Ubuntu 24.04, `install.sh` поставит Docker и настроит nginx + TLS сам.

Всё остальное (Docker, reverse proxy, файервол) `install.sh` может настроить за тебя — см. ниже.


## Быстрый старт

### Вариант 1 — автоустановка (рекомендуется)

Подходит для полностью пустого сервера — например, свежий VPS с Ubuntu 24.04.

```bash
git clone https://github.com/Butenko-oleg/DDNS.git
cd DDNS
sudo ./install.sh
```

Первым делом скрипт спросит схему установки:

| Схема | Когда выбирать | Что произойдёт |
|---|---|---|
| **1** | один сервер, оба нейм-сервера на нём | полная установка: база, PowerDNS, админка, зона; NS1 и NS2 указывают на один IP |
| **2** | этот сервер — **ns1** из двух | то же самое, плюс вопрос про IP второго сервера: сразу включит отдачу зоны (AXFR по TSIG) и напечатает ключ для ns2 |
| **3** | этот сервер — **ns2** (вторичный) | только DNS: спросит IP первичного и TSIG-ключ, поднимет dnsdist + PowerDNS и заберёт зону. Ни админки, ни базы здесь не будет |

Дальше (для схем 1 и 2) скрипт спросит только то, что реально требует решения человека: домен/зону, имена нейм-серверов, IP сервера, логин админки, порты для файервола. Всё остальное (пароли, ключи) сгенерирует сам. Дальше он:

1. поставит Docker, если его ещё нет (спросит подтверждение);
2. создаст `.env` и `powerdns/pdns.conf` с настоящими секретами;
3. поднимет `docker compose up -d`;
4. дождётся готовности PowerDNS;
5. создаст DNS-зону и правильно настроит NS/SOA/A-записи в апексе (с `@` вместо повторения имени зоны — иначе получится задвоенное имя, известные грабли `pdnsutil`; и сразу с коротким негативным TTL в SOA — 5 минут вместо часового дефолта, чтобы клиентские резолверы вроде MikroTik не залипали на устаревшем "такой записи нет");
6. по желанию настроит файервол (`scripts/setup-firewall.sh`);
7. по желанию настроит nginx + Let's Encrypt (`scripts/setup-reverse-proxy.sh`) — но только если делегация домена у регистратора уже распространилась, иначе предложит сделать это позже отдельной командой;
8. покажет и сохранит в `install-summary.txt` всё, что понадобится дальше: адрес админки, логин/пароль, DNS-ключи, и что ещё нужно сделать руками (единственное, что скрипт принципиально не может — прописать NS-делегацию у регистратора, это на его стороне).

Последовательность для двух серверов: сначала схема **2** на первом (он напечатает TSIG-ключ), затем схема **3** на втором — введёте тот же ключ. Подробности — в разделе [Второй нейм-сервер](#второй-нейм-сервер-резервирование-dns).

`install-summary.txt` содержит секреты открытым текстом — сохраните его в менеджере паролей и удалите с сервера (`shred -u install-summary.txt`).

Безопасно перезапускать — спросит перед перезаписью `.env`/`pdns.conf`, пропустит создание зоны, если она уже существует.

### Вариант 2 — руками, по шагам

```bash
git clone https://github.com/Butenko-oleg/DDNS.git
cd DDNS

cp .env.example .env
nano .env   # заполни реальными значениями — см. таблицу ниже

cp powerdns/pdns.conf.example powerdns/pdns.conf
nano powerdns/pdns.conf   # вписать те же DB_PASSWORD и PDNS_API_KEY, что в .env

docker compose up -d
```

При самом первом старте Postgres автоматически выполнит `init.sql` (это происходит только один раз, на полностью пустом каталоге `./postgres`) и создаст всё сразу: схему PowerDNS, таблицу `ddns_clients` и `admin_credentials`.

### Что заполнить в `.env`

> При установке через `install.sh` всё это заполняется автоматически — таблица нужна, если ставите вручную (Вариант 2) или хотите понять, что означает каждое значение.

| Переменная | Что это |
|---|---|
| `ADMIN_USER` / `ADMIN_PASSWORD` | Стартовый логин для `/admin`. Пароль потом лучше сменить прямо в интерфейсе — см. ниже. |
| `DDNS_ZONE` | Твоя зона, например `ddns.example.com` |
| `PDNS_API_KEY` | Случайная строка — общий секрет между `ddns-api` и API PowerDNS |
| `DB_NAME` / `DB_USER` / `DB_PASSWORD` | Креды Postgres, общие для `postgres` и `ddns-api` |
| `PUBLIC_SCHEME` | `https`, если только не тестируете локально без TLS |

Генерируй нормальные случайные значения, а не что-то короткое:

```bash
openssl rand -base64 24
```

### Важный нюанс: `pdns.conf` — не через `.env`

Официальный образ PowerDNS читает из переменных окружения **только API-ключ** (и то не так, как хотелось бы — см. ниже), а **пароль от БД** обязан жить в `powerdns/pdns.conf` открытым текстом. Поэтому:

- `powerdns/pdns.conf` — этот файл в `.gitignore`, то есть твои реальные секреты никогда не попадут в git.
- `gpgsql-password=` и `api-key=` в `pdns.conf` должны **вручную** совпадать с `DB_PASSWORD` и `PDNS_API_KEY` из `.env` — синхронизации между файлами нет, это два независимых места.

> Официальный образ поддерживает `PDNS_AUTH_API_KEY` как переменную окружения для ключа API — но у неё есть неочевидный побочный эффект: она заодно выставляет `webserver-password`, что требует HTTP Basic Auth поверх `X-API-Key` и ломает обычных клиентов вроде `ddns-api`. Поэтому этот проект сознательно не использует этот механизм и держит ключ строкой в `pdns.conf`.

### Создать зону и делегировать её

> Если ставил через `install.sh` — зона и NS/SOA/A-записи уже настроены автоматически, эта секция нужна только для справки или если что-то нужно поправить руками.

Сам проект зону не создаёт — это делается один раз после первого старта:

```bash
docker compose exec powerdns pdnsutil create-zone example.com ns1.example.com
```

У регистратора домена (там, где куплен `example.com`) прописываются нейм-серверы — например:
```
ns1.example.com → <IP-сервера>
ns2.example.com → <IP-сервера>   (можно тот же IP, если сервер один)
```

Это называется glue-записи — они нужны, потому что имя нейм-сервера находится внутри собственной делегируемой зоны. **Этот шаг install.sh сделать не может** — это вне сервера, на стороне регистратора, и всегда делается руками.

**Важные грабли с `pdnsutil`:** если добавлять записи в апекс зоны (саму `example.com`, а не поддомен) через `pdnsutil replace-rrset`, то имя апекса нужно указывать как `@`, а не повторять `example.com` — иначе получится задвоенное имя `example.com.example.com` (относительное имя добавится поверх зоны), и `check-zone` покажет ошибку `SOA record not at apex`. Пример правильной команды:

```bash
docker compose exec powerdns pdnsutil replace-rrset example.com @ NS "ns1.example.com." "ns2.example.com."
docker compose exec powerdns pdnsutil replace-rrset example.com ns1.example.com A <IP>
docker compose exec powerdns pdnsutil replace-rrset example.com ns2.example.com A <IP>
```

Заодно стоит прописать SOA явно, с коротким **негативным TTL** (последнее поле, MINIMUM) — дефолт PowerDNS для него обычно час, а это означает, что любой резолвер клиента (например, домашний роутер), спросивший про домен на секунду раньше, чем появится запись, запомнит "такой записи нет" на целый час — и без ручного сброса кэша на клиенте ничего не поменяется. `install.sh` делает это автоматически; при ручной настройке это нужно сделать самому:

```bash
docker compose exec powerdns pdnsutil replace-rrset example.com @ SOA "ns1.example.com. hostmaster.example.com. $(date +%Y%m%d)01 10800 3600 604800 300"
```

Проверить зону на ошибки:
```bash
docker compose exec powerdns pdnsutil check-zone example.com
```
Должно быть `0 errors, 0 warnings`.

### Reverse proxy / TLS

`ddns-api` слушает только `127.0.0.1:8000` — перед ним обязательно должен быть reverse proxy с TLS. По HTTP доступа нет, и не задумано.

> `install.sh` в конце предлагает настроить это автоматически — nginx + Let's Encrypt (certbot). Эта секция нужна, если при установке отказались, хотите перенастроить отдельно или используете что-то другое (Caddy/Traefik).

**Автоматически (nginx + certbot):**

```bash
sudo DOMAIN=ddns.example.com EMAIL=you@example.com ./scripts/setup-reverse-proxy.sh
```

Запускать **только после того**, как делегация NS у регистратора уже распространилась — скрипт сначала проверяет, что домен реально резолвится на этот сервер, и откажется продолжать, если нет (чтобы не тратить впустую лимит попыток Let's Encrypt). Если рано — подождите и запустите ещё раз, скрипт безопасно перезапускать.

`EMAIL` не обязателен (Let's Encrypt использует его только для писем об истечении сертификата), но лучше указать. Автопродление сертификата certbot настраивает сам через systemd-таймер — руками ничего продлевать не нужно.

**Вручную, если используется не nginx** — пример на Caddy:

```
ddns.example.com {
    reverse_proxy 127.0.0.1:8000
}
```

### Файервол

> `install.sh` предлагает настроить файервол сам в конце установки — эта секция нужна, если при установке отказались или хотите перенастроить отдельно.

```bash
sudo ./scripts/setup-firewall.sh
```

Скрипт ставит и настраивает UFW вместе с [`ufw-docker`](https://github.com/chaifeng/ufw-docker) (без него правила UFW не действуют на порты, опубликованные через Docker — частая ловушка). Открывает только: SSH, `80`, `443`, `53/tcp`, `53/udp`. Всё остальное — блокируется, включая PowerDNS API и Postgres, которые и так не публикуются наружу через `docker-compose.yml`.

Если порты нестандартные:
```bash
sudo SSH_PORT=2222 HTTP_PORT=8080 HTTPS_PORT=8443 ./scripts/setup-firewall.sh
```

Запускать **после** `docker compose up -d` (скрипту нужно найти контейнер PowerDNS по имени).

Проверить снаружи (с другой машины, не с самого сервера):
```bash
nmap -Pn <IP-сервера>
```
Должны быть открыты только разрешённые порты — и ничего больше.


## Работа с админ-панелью

Откройте `https://<ваш-домен>/admin` и войдите с `ADMIN_USER`/`ADMIN_PASSWORD` из `.env`.

- **Новый хост** — создаёт пару hostname + секретный токен.
- **Быстрая настройка** (иконка рядом с хостом) — готовые значения для TP-Link Omada, Keenetic, MikroTik, Windows и macOS/Linux, с реальным токеном и адресом сервера. У обычных домашних TP-Link/D-Link кастомного DDNS-провайдера нет вообще — вкладка объясняет обходной путь (гонять скрипт с любого постоянно включённого устройства в той же сети).
- **Изменить / включить-выключить / удалить** — самоочевидно; выключение останавливает обновления хоста, не удаляя токен.
- **Настройки (шестерёнка)** — смена логина и/или пароля админки (пароль можно оставить пустым, чтобы поменять только логин). Действует сразу; `ADMIN_USER`/`ADMIN_PASSWORD` из `.env` перестают использоваться после первого сохранения через интерфейс.
- **Заблокированные IP (иконка щита)** — список забаненных `fail2ban`'ом адресов по каждому jail'у, с кнопкой «Разбанить» у каждого IP (применяется до минуты — см. раздел про `fail2ban` ниже) и кнопкой скачать список как `.txt`. Требует настроенных cron-скриптов — без них покажет "нет данных".


## Обновление проекта

```bash
git pull
docker compose build ddns-api
docker compose up -d
```

Данные Postgres и зона PowerDNS хранятся в `./postgres` — обычный `docker compose up -d` после `git pull` их не трогает.


## Заметки по безопасности

- Rate limiting на подбор пароля/токенов — встроен в приложение, но состояние живёт в памяти процесса и сбрасывается при перезапуске. Для чего-то серьёзно смотрящего в интернет — дополнительно стоит рассмотреть rate limiting на уровне reverse proxy (nginx `limit_req`, Cloudflare и т.п.).
- PowerDNS API (порт 8081) **не публикуется** наружу — доступен только `ddns-api` внутри Docker-сети. Не добавляйте `ports:` для него без необходимости, а если добавляете — только на `127.0.0.1`.
- Делайте бэкапы `./postgres` (там и зона DNS, и все токены хостов) и `.env` за пределы сервера. Потеря `.env` не теряет данные, а потеря `./postgres` — теряет. Готовый вариант — `scripts/backup.sh`: собирает дамп, зону текстом, конфиги, nginx, сертификаты и cron в зашифрованный архив и проверяет, что он читается; `scripts/restore.sh --verify-only` разворачивает дамп в отдельный контейнер и считает строки.
- **Секреты живут только в `.env` и `powerdns/pdns.conf`** — оба файла в `.gitignore`. Если конфиг куда-то уходил (публикация форка, переписка, архив с бэкапами), считайте `PDNS_API_KEY` и `DB_PASSWORD` скомпрометированными и смените оба: они дают полный контроль над записями зоны. Новые значения — `openssl rand -base64 24`, менять сразу в двух местах и перезапускать стек.
- SSH — только по ключу, `PasswordAuthentication no` в `sshd_config` (сначала проверьте, что вход по ключу работает, и только потом отключайте пароль).
- `fail2ban` для SSH **и** для админ-панели/DDNS-токенов:
  ```bash
  sudo ./scripts/setup-fail2ban.sh
  ```
  Важный нюанс: `ddns-api` стоит за reverse proxy, поэтому в его собственных логах виден IP nginx, а не реального атакующего. Приложение отдельно пишет неудачные попытки входа в `./logs/auth.log` с уже правильно определённым реальным IP (через `X-Forwarded-For`) — именно этот файл и читает `fail2ban`, а не логи самого контейнера. Банит по трём направлениям: SSH (`sshd`), неверный пароль админки (`ddns-admin`, 5 попыток/10 мин), неверный DDNS-токен (`ddns-token`, 3 попытки/10 мин — токены случайные, пары попыток обычно достаточно, чтобы считать это атакой).

  Бан **бессрочный** (`bantime = -1`) — снимается только руками, автоматически не истекает.

  Список забаненных и разбан — прямо в админке (иконка щита в шапке), включая кнопку «Разбанить» у каждого IP. Технически это два cron-скрипта на хосте (`fail2ban` живёт на хосте, `ddns-api` — в Docker, прямого доступа между ними нет):
  - `export-fail2ban-status.sh` — раз в минуту выгружает статус в `./logs/banned-ips.json`, который читает приложение;
  - `process-unban-queue.sh` — обрабатывает запросы на разбан, которые кнопка в админке кладёт в `./logs/unban-queue.txt` (задержка применения — до минуты).

  ```bash
  chmod +x scripts/export-fail2ban-status.sh scripts/process-unban-queue.sh
  crontab -e
  ```
  ```
  * * * * * /opt/ddns/scripts/process-unban-queue.sh && /opt/ddns/scripts/export-fail2ban-status.sh >/dev/null 2>&1
  ```

  Разбанить и вручную, минуя админку: `fail2ban-client set ddns-admin unbanip <IP>`
  Посмотреть статус: `fail2ban-client status ddns-admin`
  (укажите реальный путь к проекту)


## Диагностика

**Роутер пишет "bad auth" / DNS не обновляется.** Проверьте, что `hostname=` в запросе — это полный домен (`host.вашазона.ru`), а токен/пароль скопирован свежим из «Быстрой настройки», не набран руками.

**Omada не принимает Update-URL.** В поле нужны буквально `[USERNAME]`/`[PASSWORD]`/`[DOMAIN]`/`[IP]` — «Быстрая настройка» уже их подставляет, руками менять не надо.

**curl/скрипт получает редирект вместо ответа.** Убедитесь, что используется `https://` из «Быстрой настройки», а не `http://` — обычный HTTP не обслуживается.

**Ошибка `{"detail":"Unauthorized"}` от `/nic/update`.** Это не про токен хоста — это PowerDNS отвечает `401` на несовпадающий `api-key`, а код приложения заворачивает это в JSON. Проверьте, что `api-key=` в `pdns.conf` и `PDNS_API_KEY` в `.env` — идентичны, и что PowerDNS реально перезапущен после правки (`docker compose up -d --force-recreate powerdns`).

**cron на macOS не срабатывает.** macOS не выполняет `cron`, пока ноутбук спит — это нормально, просто пропустит несколько срабатываний. Если не работает даже при включённом Mac — дай Терминалу/`cron` разрешение Full Disk Access в Настройках → Конфиденциальность и безопасность.

**Свежий `git clone` + `docker compose up -d` не поднимается.** Проверьте `docker compose logs postgres` — если каталог `./postgres` не был пустым (например, что-то уже туда писалось), `init.sql` не выполнится. Либо удалите каталог и начните заново, либо накатите нужные `CREATE TABLE` из `init.sql` вручную.

**SOA зоны показывает `a.misconfigured.dns.server.invalid`.** Значит зона создана без нормальной SOA-записи. См. раздел [Создать зону и делегировать её](#создать-зону-и-делегировать-её) — обратите внимание на `@` вместо повторения имени зоны.

**Роутер (например, MikroTik) не резолвит новый хост сразу, помогает только ручной сброс DNS-кэша.** Скорее всего роутер успел спросить про хост *до* того, как появилась запись, и закэшировал негативный ответ на срок из поля MINIMUM в SOA — если там дефолтный час, столько и придётся ждать (или сбрасывать кэш руками) при каждом промахе. `install.sh` уже ставит MINIMUM=300 (5 минут); если зона создавалась руками до этого фикса — понизь его так же, как в разделе про SOA выше, и один раз сбрось кэш на клиенте, чтобы избавиться от уже закэшированного часового негатива.

## Второй нейм-сервер (резервирование DNS)

Домену нужны минимум два NS на **разных** адресах: если оба указывают на один сервер,
его падение уносит зону целиком. Комплект `ns2/` поднимает вторичный PowerDNS,
который забирает зону с основного по AXFR и продолжает отвечать, если основной недоступен.

```
ns1 (этот сервер)                    ns2 (вторая площадка)
PowerDNS + PostgreSQL      ──AXFR──▶ dnsdist :53 → PowerDNS (LMDB)
принимает изменения                   только читает зону
```

Порядок:

1. на основном сервере — `sudo ./scripts/enable-axfr.sh --peer <IP второго NS>`,
   скрипт включает отдачу зоны и печатает TSIG-ключ;
2. на второй машине — `cp ns2/ns2.env.example ns2/ns2.env`, заполнить и выполнить
   `sudo ./ns2/setup-ns2.sh`;
3. проверить `ns2/check-ns2.sh` — зона приехала, ответы совпадают с основным;
4. поменять A-запись второго NS в зоне и glue у регистратора.

Важно: `refresh` в SOA задаёт, как часто вторичный проверяет изменения. По умолчанию
в PowerDNS это часы — для DDNS-зоны ставьте 120–300 секунд, иначе вторичный будет
отставать надолго.
